## Evidence and source hazards

The [original production baseline](../performance/2026-09-28-profile.md) transferred about 1.34 MiB on mobile reviews. Lighthouse estimated 636 KiB of image-delivery savings across covers and textures. That estimate used DPR 1.75 and must not become a budget that forces blur at DPR 3 or 4.

- [reviews/index.astro](../../src/pages/reviews/index.astro) asks `resolveCover` for one 500 × 800 image per review.
- [covers.ts](../../src/lib/covers.ts) resolves original sources and generates WebP at quality 70. Generate variants from those originals, not from an already resized 500 px output. Preserve explicit/co-located/bundled/placeholder source selection and other callers' behavior.
- [types.ts](../../src/lib/types.ts) currently transports a single `Post.img` URL. Extend serialized image metadata compatibly and inspect every `Post` producer/consumer.
- [ReviewCard.svelte](../../src/components/ReviewCard.svelte) uses the same source in wide, cover, and tier layouts. It explicitly corrects `src` after hydration to prevent wrong-book covers when SSR rank order differs from `?o=0` order. Preserve that fix across `src`, `srcset`, and `sizes`; the attributes must always describe the same book. The tier caption samples the loaded image on a canvas.
- [main.css](../../src/styles/main.css) and [fancy.css](../../src/styles/fancy.css) define card sizes. Measure the image box, not just grid-column width or the width attribute.
- [screenshot.ts](../../src/lib/screenshot.ts) uses snapdom and a DPR-derived export scale capped at 2, with side/area limits. Source selection during export may differ from on-screen `currentSrc`; inspect the installed library and the downloaded result.

The shared helper also supplies flowchart covers at different dimensions. Do not overwrite the previous graph optimization or globally reduce quality for unrelated pages.

## Implementation sequence

1. Baseline the inherited production build and inventory original image dimensions, aspect ratios, formats, and bytes. Select representative covers: tiny title lettering, fine line art, faces, gradients, dark texture, and a low-resolution original. Preserve those originals.
2. Measure rendered image dimensions in every review layout and target viewport. Select a bounded set of generated widths from that demand. Include sufficient candidates for DPR 3 and 4 when the originals contain that detail. Do not impose a blanket 500 px or 2× cap.
3. Generate candidates with Astro's build-time image pipeline and serialize the metadata to the Svelte island. Use honest width descriptors with layout-aware `sizes`, or an equivalent supported approach. Do not import Astro components inside Svelte. Keep intrinsic geometry stable to avoid layout shifts and preserve the existing crop/framing.
4. Preserve the post-hydration image correction. Verify both direct navigation to sorted/filtered URLs and subsequent layout changes. Avoid transient wrong-book images and redundant low-resolution-then-high-resolution requests caused by incorrect attributes.
5. Choose encoding settings through visual comparison. Do not lower the current quality setting as the default strategy. If an original can support visibly better detail than the existing rendition, prefer that improvement. Do not enlarge a small original and claim it contains more detail.
6. Verify screenshot export gets sufficient-resolution sources even for offscreen cards. Retain lazy loading for ordinary browsing, caption tinting, bookmarks, video covers, and existing export size limits. Make export-specific resolution changes only when required to prevent a regression.

Texture optimization is a separate optional experiment after covers pass. Preserve the original and inspect gradients, grain, tiling, and overlays at high DPR. Do not trade visible artifacts for the estimated 130 kB texture saving. Avoid adding an image CDN, runtime resizing service, or framework upgrade.

## High-resolution quality gate

Use the standard skill profiles for comparable performance numbers. Add a browser quality matrix using these CSS viewports and DPRs; these are test conditions, not claims of testing physical device models:

- 375 × 812 at DPR 3.
- 390 × 844 at DPR 3.
- 430 × 932 at DPR 3.
- 412 × 915 at DPR 4.
- Desktop 1350 × 940 at DPR 1 and DPR 2.

For each viewport, test wide, cover, and tier layouts, including direct URL entry and transitions between layouts. Verify a resized/rotated mobile view and a browser zoom-in where supported. Use Chromium and WebKit for high-DPR mobile behavior where available, and state any missing browser or physical-device coverage.

For representative covers, save the selected `currentSrc`, CSS image bounds, DPR, original dimensions, selected file dimensions, and transferred bytes. **Read the selected file's actual pixel dimensions** using image metadata. Browser `naturalWidth` is density-corrected and cannot alone prove the selected resource's pixel resolution. [MDN explains this distinction](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/naturalWidth).

As an initial sizing check, compare source pixels to displayed CSS pixels × DPR in both dimensions, accounting for cropping/transforms. For example, a 180 CSS-pixel-wide cover needs roughly 540 source pixels at DPR 3 and 720 at DPR 4. This is a resolution floor when the original permits it, not proof of visual quality. Width descriptors and `sizes` must reflect the actual rendered size; the browser chooses among candidates. See [MDN's image reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img).

Capture before/after screenshots at native device scale, without resizing them for comparison. Inspect native-pixel crops of lettering, edges, faces, and texture against both the previous output and a high-quality reference derived from the original at the same display geometry. Do not accept new blur, ringing, blockiness, banding, or changed framing. Do not rely on a downscaled contact sheet, a Lighthouse image warning, or a resolution ratio as the sole quality verdict.

If an original is too small, record the limitation and serve its best available detail. Do not silently downgrade other covers to that ceiling. If quality and a byte target conflict, preserve quality and report the tradeoff.

## Functional and export checks

Add a focused, repeatable script such as `scripts/verify-review-image-quality.mjs` for candidate selection and behavior. It must check:

- Each visible card's title, link, alt text, and selected image identify the same book after hydration, rank/recent sort, filters, reset, bookmarks, and all layout changes. Include cold navigation to `?o=0` and a filtered/sorted URL.
- Deferred images load when brought into view, with stable dimensions and no broken candidates. Video covers and deterministic placeholders retain their behavior.
- Tier caption color is recalculated for the correct selected cover after changes, without tainted-canvas errors or stale colors.
- Downloaded screenshots remain sharp for short lists at high DPR and complete for long lists with offscreen covers, across all layouts. Wait for required decodes, inspect downloaded pixels, and verify the existing format/size-limit handling. A successful download alone is insufficient.
- Brief 1's graph regression command and Brief 2's font/export checks still pass for affected shared code. Check representative individual-review and OG pages if shared image resolution changes reach them.
